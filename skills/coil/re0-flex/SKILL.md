Read a repository's history, sessions, rules and checks once, keep them current by their changes alone, and answer each new request with a short bundle drawn from cited procedure cards.

## Goal

The next request in a repository should reach its first useful action sooner and be corrected less often, because the agent already knows how this repository does that kind of work. The sources are the git log (commit messages, changed files, dates), the agent session logs (requests, tool calls, corrections, verification results), and the repository's own rule documents and check scripts. They are read in full once, when the memory is built; every later run reads only what changed since, because re-reading everything per request spends the latency this skill exists to save.

The run produces three things. **Procedure cards**, one per kind of work: its trigger, the state it assumes, the order of steps, the repository's existing check commands, the evidence that shows it finished, the conditions under which it must not be applied, and the counterexamples that mark its edge. **An evidence index** on every card, naming the source location, commit and session behind each claim, so the card inherits the authority of its sources and no more. **An execution bundle** per request, a few lines naming the relevant cards, where the current state differs from what they assume, and what is still unconfirmed.

Past records are a biased sample of particular situations, never the answer key. A commit is not proof that the work succeeded, silence after it is not approval, and a correction may have held only for the case it corrected. A rule frozen from such records only makes the wrong move faster. So every card carries its applicability conditions and counterexamples beside its steps, and a case with no verification result and no explicit acceptance stays a hypothesis.

Repeated deterministic work leaves the cards and becomes a tool, a gate or a scheduled run. Three judgments stay with the human: whether one correction becomes a lasting preference, which of two conflicting rules wins, and whether sensitive material may be published.

## Workflow

1. **Collect events.** From this skill's folder run `node scripts/events.mjs events --repo <path> [--sessions <dir>]... [--since-cursor <file>] --out <events.jsonl> [--json]`. Input: the repository and one `--sessions` per folder of session logs, each file read in the format it is written in; with no `--sessions` the run reads the Codex and Claude Code session folders under `CODEX_HOME` and `CLAUDE_CONFIG_DIR`, or their defaults in the home folder. Output: one event per line in the events file, of kind `commit` (sha, date, subject, changed files), `request`, `correction` (a user message after an assistant turn), `tool`, or `verification` (a check result read from a finished command: a test runner's own summary, a lint or type-check's exit code when the command was that single invocation, or a CI result from unfiltered `gh run view|list --json` output, with its check kind, runner, result, counts, exit code, working folder and a `compound` flag for a command whose exit code belongs to its last statement). Each event has an id derived from its content, its source file and line, its session, and for session events the link that tied it to the repository: `cwd` when the session's working folder is inside it, `tool` when a tool ran there by its working folder or a file argument. A path named only in injected context ties nothing. Events already in the file collapse by id, so a session reached through two folders is counted once. With a cursor file the run appends only what is newer than the cursor and rewrites it, so the first run with a new cursor is the one full read and every later run is incremental. Exit codes: 0 collected, 2 a usage error or an unreadable input. The summary lists the folders read and counts the files of no known format and every record type it skipped; read those counts, since a format the script does not know yet shows up there before it shows up as a missing card.
2. **Read the rules and checks once.** Read the repository's agent guide, contributing guide and every check script or gate it runs, and list each check command with what it protects. Later runs reread only the files whose commits appear among the new events.
3. **Cut the events into episodes.** An episode is one piece of work: request, target state, action, correction, verification result. A session can hold several episodes and one episode can span several sessions and commits. Tie sessions to commits by repository, branch, files, commit ids and tool calls, never by time alone, and hold any tie you cannot support; an event linked by `tool` comes from a session that worked elsewhere, so it is the weaker tie and is checked before a card cites it.
4. **Classify episodes by what they did.** The axes are purpose, target, state change and completion evidence, not wording: two requests phrased differently that both turned a hand-copied fact into a derived one are one type, and two "doc cleanups" where one fixed tone and one established a single source are two. Use similarity of text only to find candidates and decide by diff shape, tool order and check results. Allow several labels and allow holding an episode unlabeled. A correction marks where a type ends, so it becomes a counterexample on the card. A keyword or regular-expression classifier is a baseline to compare against and never the classifier of record.
5. **Write the cards.** One Markdown file per card, named for the kind of work it covers, under `.re0/flex/cards/` (the events file and the cursor sit beside it in `.re0/flex/`; keep any folder the repository ignores if it has no `.re0/`), readable by a person and carrying exactly one fenced block whose info string is `json card`. The block holds `status` (`hypothesis` or `accepted`), `evidence` (a list of `{ "event": <id>, "role": <role> }`, with roles such as `origin`, `correction`, `counterexample`, `verification`, `acceptance`) and `watch`, the hash of each rule document or check script the card relies on. Get `watch` from `node scripts/events.mjs hash --repo <path> <file>...`, which prints it ready to paste. Mark a card `accepted` only when it cites a verification result or an explicit acceptance; everything else is a hypothesis.
6. **Check the cards.** Run `node scripts/events.mjs cards-check --cards <dir> --events <events.jsonl> [--repo <path>] [--json]`. It reports a card citing an event that is not in the events file, a card with no evidence or no single card block, an `accepted` card with no cited `verification` or `acceptance` event, and a card whose watched file is gone or changed since its hash was taken, which marks it for re-review. Exit codes: 0 no finding, 1 findings, 2 a usage error or an unreadable input. A re-review card is reread against the changed file before it is used again; never silence it by retaking the hash alone.
7. **Answer a request with a bundle.** Run step 1 with the cursor and step 6, then pick the cards whose trigger matches the request. The bundle states, in a few lines, which cards apply and why, where the current state differs from their preconditions, which do-not-apply condition or counterexample is close, and what is unconfirmed. It cites card names and event ids and never pastes the sources. When no card fits, say so and work from the repository itself.
8. **Move repeated deterministic work out.** When the same mechanical steps recur across episodes and their inputs decide their result, propose a script, a gate or a scheduled run in the repository's own tooling, with the episodes that show the repetition. The proposal splits the work by what decides each step: the tool takes the steps whose inputs decide their result, the steps that need meaning stay on the card, and each decision the judgment makes is written to a file the tool reads on its next run, so a rerun replays it. A proposed gate comes with a violation it fails and a valid case it passes. The human approves before anything is wired into the repository's checks or schedules.
9. **Hand the judgments back.** Ask the human, with the cited events, whenever a card would turn one correction into a lasting preference, when two rules or cards conflict and their order matters, and when a card, bundle or event quotes material whose publication is in doubt.
10. **Measure use, not labels.** The worth of the memory is time to the first useful action, total tokens including building and refreshing it, and the re-correction rate on new work, set beside the same work done without it. Classifier quality is measured only against a sample a person labeled independently, stratified by repository, period and rare type, split by time so derived cases of one piece of work do not land on both sides, reporting precision, recall, over-merging and hold rate per type beside the keyword baseline. Until that sample exists, claim no precision.
11. **Taste-test before calling it done**: call the Skill tool with "sip".

## Rules

- A card is a hypothesis until it cites a verification result or an explicit acceptance. A verification is a `verification` event whose result shows the card's completion check passing on that work, read from the runner's summary when the command was `compound`; an acceptance is a `request` event in which the human accepts the outcome in words. A commit, a merged change or a quiet session is neither. An event the script marks `correction` is only a candidate: confirm from its text that it corrected something before a card cites it as one. Promoting a card to `accepted` on a correction alone is the human's call.
- Every card carries do-not-apply conditions and counterexamples beside its steps; a card that lists only steps is incomplete.
- Read everything once, at build time: the first run in a repository, or a run the human asks to rebuild. After that each run, started when the human invokes the skill or a request arrives in a repository whose `.re0/flex/` already exists, reads only the changes through the cursor; a per-request full reread defeats the purpose. The bundle for a request is part of the reply that starts the work, not a file.
- The script owns the event format, the ids, the cursor and the card checks. Name its commands, flags and exit codes and never restate its parsing; never edit the events or cursor file by hand.
- Session tolerance is the script's: unknown record types are skipped and counted, never fatal. A rising skip count for a type that carries requests or tool calls is a reason to extend the script, not to read the logs by hand.
- The events file and the cards quote raw session text, so they stay in a folder the repository ignores. Publishing any of it, and promoting a correction to a lasting rule, and ordering conflicting rules, wait for the human.
- A deterministic step becomes a tool, gate or schedule only through a proposal the human approves; it never stays as prose the agent re-derives per request.

## Verification

Before finishing, confirm:

1. The events run's summary is in the report, with what it added by kind, the duplicates collapsed and the skipped record types, and whether it ran from a cursor.
2. Every card has a single card block, cites only events the events file holds, carries do-not-apply conditions and counterexamples, and is `accepted` only with a cited verification or acceptance.
3. `cards-check` exits 0, or each finding is fixed or reported, and every re-review card was reread against its changed file.
4. Each bundle names its cards, the differences from the current state and the unconfirmed items, and stays short.
5. Every proposal for a tool, gate or schedule, and every one of the three human judgments, is named as open until the human answers.
6. No precision or recall is claimed without an independently labeled sample.
