Use when someone states a goal but does not know which skills serve it or in what order, asks which skills to use, or wants a job that needs several skills run end to end. Turn one stated intent into an ordered skill graph, show it, and run the steps the session may run.

## Goal

Someone who does not know this suite's catalog should be able to say what they want and see every part of it done, with nothing misread or dropped. Read the intent into numbered requirements, select and order the installed skills that serve them, check the plan with the bundled script, show the whole plan before anything runs, run each step the session holds authority for, and stop at the first step that needs the human, with a report of what ran and of every requirement. Coordination writes nothing of its own: the plan and its report live in the conversation.

## Workflow

1. Read the human's stated intent and the installed roster from the host catalog or skill directories. If given only live state without a stated intent, ask for the intent rather than infer it. Read each candidate's contract and invocation lane: `disable-model-invocation: true` in its SKILL.md, or `policy.allow_implicit_invocation: false` in its `agents/openai.yaml`, means user-only; otherwise it is model-invoked, and when the two disagree it is user-only.
2. Read the intent through readback: call the Skill tool with "readback" on the intent as the human wrote it, and wait for the answer to any question it asks. This is how the router reads the request, not a planned action: it reads and writes nothing beyond the conversation, is never listed in the graph or counted among its actions, and runs on a request for the order alone too. Turn the confirmed read into numbered requirements (`r1`, `r2`, ...), one per thing the human asked for, in their order, plus one line beginning `understood as: `. Skip it only when the intent names one installed skill and its one target and asks nothing else (`single-named-step`). When readback is not installed, read the intent into requirements yourself and say the read went unchecked.
3. Select, for each requirement, only skills whose triggers and outputs serve it. If no installed skill serves any requirement, there is no plan: say plainly that the goal was not done and why, run nothing and check nothing. A frozen pipeline (a skill whose own contract runs a fixed sequence of other skills) that already serves a requirement is one node, never expanded; read its members only to type it, so the node counts as writing when any member writes and is a `user-handoff` when any member is user-only. If one skill suffices, use exactly one node and say ordering is trivial. A skill the intent or a selected contract calls for that the roster lacks stays as a `skip` step, shown as unavailable, and when a selected step needs its output the run ends with the stop condition unmet, never as a silent skip. A requirement nothing installed serves is recorded as unmet with the reason. Work a requirement needs that no installed skill covers and no one named a skill for (a local rebase, writing a check) is a step of its own, typed by the table below. Do not pad the graph, require an orientation skill, invent a pipeline skill, or substitute another skill for a missing one.
4. Close each stretch that writes with one `sip` check (the suite's taste test for new output), run as one node: the last step before each handoff, or before the end, after every write since the previous stop, a human's write counting once its result comes back. A stretch that writes nothing gets none, and a frozen pipeline that runs `sip` itself closes its own writes. When the run delivers a judgment no `sip` tastes (a verdict or a choice with no file), add one outside read after it instead: `shower` for whether it reads clearly to someone with no context, `factchk` for claims about the world, `mandela` for an eval, metric or experiment; never both. An added check serves the requirements of the steps it checks and is shown with its reason, never counted as an action.
5. Order the selected steps by their contracts' prerequisites: a step depends on another when its firing precondition needs that step's output. Detect cycles before showing the graph; if one exists, the whole result is a `reject` naming the cycle in run order, each arrow pointing from a step to the one that needs its output, such as `skill-a -> skill-b -> skill-a`, with no steps and no partial order. List the steps in run order, and where the prerequisites leave the order free put the session's own steps before a handoff, so the run reaches the human once and as late as it can. Give the graph one observable stop condition, the state that means every requirement was served, reached only after its last step; a no-match or a `reject` ends at its own report.
6. Give every step an identifier, a target (the skill that acts, the work when no skill covers it, or the question when the step is a human decision), predecessor identifiers, the requirements it serves, exactly one type, firing precondition, expected output (for a skill, limited to its own contract), skippable condition, cost owner, its target's lane, and whether it writes: creates or changes content (a file, document, record or message), where moving content that already exists (a push, a tag, a publish) does not count. Assign its type by the first row below that applies, so a missing user-only skill is a `skip`. Where a contract does not say whether its skill writes, count it as writing; where its lane cannot be read, count it as user-only. A step whose type depends on a predecessor's output is shown as conditional with the types it can take and the condition that decides, and typed once that output exists.

   | Type | Meaning and precondition | Cost owner |
   | --- | --- | --- |
   | `skip` | The step does not run, and the graph goes on without it: condition not applicable, skill not installed, or no authority that anyone present could grant. A step that depends on it is skipped too, its reason naming the step it lost. | None. |
   | `user-handoff` | The human acts: the target is user-only, the step is destructive or irreversible, a human decision is needed, or the work needs authority the human holds and the session does not. | The human's time, at their discretion. |
   | `invoke-model-skill` | The router runs it: none of the rows above applies, so the target is installed and model-invoked, the session already holds authority for the work, and the step is neither destructive nor irreversible. | This run's budget. |
   | `session-step` | The session does the work itself: no skill covers it, the session holds authority for it, and it is neither destructive nor irreversible; such work that is destructive or irreversible is a `user-handoff`. | This run's budget. |
   | `reject` | Not a step: the whole result when the request cannot be served as a graph, naming the cycle when cyclic. | None. |

7. For each `user-handoff`, say what the human does and what result to bring back: for a skill, the exact invocation they type, in the host's syntax with the installed name (a destructive step whose skill is model-invoked is still typed by the human); for a decision, the question and the answers that change the next step. If the host's invocation syntax is unknown, the handoff carries that question instead, asked when the plan is shown and before anything runs, never an invented command.
8. Check the plan before showing it by piping it as JSON to `node <skill>/scripts/plan.mjs -`, `<skill>` being the folder that holds this SKILL.md; it reads stdin and writes nothing. Exit 0 means every invariant holds; exit 1 names each broken one, which is fixed and checked again; exit 2 is a usage error or invalid JSON; `--json` prints the problems as JSON. Never show a plan the script refused. The plan has this shape:

   ```json
   {
     "readback": "ran",
     "understood_as": "understood as: <the confirmed read>",
     "requirements": [{ "id": "r1", "text": "<one thing asked>" }, { "id": "r2", "text": "<another>", "unmet": "<why nothing installed serves it>" }],
     "steps": [
       { "id": "s1", "target": "<skill>", "predecessors": [], "serves": ["r1"], "type": "invoke-model-skill", "precondition": "<when it fires>", "output": "<what its contract returns>", "skippable": "<when it may be skipped>", "cost_owner": "run", "writes": true, "lane": "model" },
       { "id": "s2", "target": "sip", "added": "sip", "predecessors": ["s1"], "serves": ["r1"], "type": "invoke-model-skill", "precondition": "s1 wrote its output", "output": "findings on that output", "skippable": "when s1 wrote nothing", "cost_owner": "run", "writes": false, "lane": "model" }
     ],
     "stop": "<the one observable stop condition>"
   }
   ```

   `readback` is `ran`, `single-named-step` or `missing`. `type` is one type, or the list a conditional step can take with the expected type first; `cost_owner` is `none`, `human` or `run` by the table, for a conditional step that of its first type; `lane` is `model`, `user` or `missing` for a skill and `none` for work or a question no skill takes. A skip adds `reason`; a handoff adds `handoff` and `bring_back`; a frozen pipeline adds `members`; a destructive or irreversible step adds `"destructive": true`; a delivered judgment adds `"judgment_only": true`; a check from step 4 adds `"added": "sip"` or `"added": "outside-read"`. A cyclic request replaces `stop` with `"reject": "<the cycle>"` over the same steps, so the script can check that each arrow is a declared edge.
9. Before any step runs, show the requirements and the `understood as:` line, then the whole typed graph in order: every field of every step, why each sits where it does, the number of actions, each added check under the steps it closes with its reason, and the stop condition; ask here for any host invocation syntax step 7 could not find. If the human asked only for the order, stop here. If any `invoke-model-skill` or `session-step` step anywhere in the graph, before or after a handoff, writes, ask once, now, for approval of the shown plan, added checks included. That approval accepts the plan and every write it shows, across a resume, until the plan changes; it grants no authority a step lacked, so it never turns a `user-handoff` into a run step. If no step to run writes, run right after showing the plan. If the human edits the plan, order it again, check it again, and show it again before running.
10. Run in order. For each `invoke-model-skill` step, call the Skill tool with that step's target, once for that step, passing the intent and its predecessors' outputs; on a host with no Skill tool, run the skill the way that host does (reading its SKILL.md and following it counts) and say so. Do each `session-step` yourself, once, within what the shown plan says. Before starting the next step, check its expected output: the file or record exists, or the skill's own report states the result. A step that does not produce its expected output failed, and the run stops there. A step whose produced output breaks a later step's precondition marks that later step and its dependents `skip` with the reason, and the run goes on with the steps that do not depend on it. Never retry by swapping in another skill, and run nothing past the last shown step.
11. Stop at the first `user-handoff` or failure. The stop report is the state a resume reads, kept in the conversation: the graph as shown, the approval status (`approved`, `not-needed`, `order-only` or `pending`), each step's `outcome` with its `result` (`ran`, `returned` for a handoff whose result came back, `skipped`, `handed-off` for the handoff the run stopped at, `failed`, or `waiting` for every step behind the stop), each requirement's `status` (`served`, `handed-off`, `waiting`, `skipped` or `unmet`, the last two with a `reason`), `stop_reached`, and the handoff with what to bring back. Pipe that report to `node <skill>/scripts/plan.mjs - --report` before giving it. When the human returns with the result in the same conversation, a new invocation reads that report and checks the result against the handoff step's expected output: a match makes that step `returned` and the run goes on from the next step under the same approval, while a changed or failed result re-plans from that step, then checks and shows the new graph before running. If the report is out of reach, start again from step 1.
12. End with the graph as shown, each step's outcome, every requirement as served, handed off, waiting, skipped with its reason, or unmet, and whether the stop condition was reached or the run stopped early at a named step (a handoff or a failure), checked with `--report` first. When a skipped or missing step's output is one the stop condition needs, say the run ended with the stop condition unmet.

## Rules

- The plan makes these decisions on every run, from the suite's working rules:
  - **The result never rests on its author.** The session that made an output judges it worst, so each stretch that writes closes with one `sip` and a delivered judgment no `sip` tastes gets one outside read (step 4), and the plan is checked by the bundled script, never by rereading it.
  - **One owner per job.** A step that would redo what an installed skill already owns is replaced by that skill; a frozen pipeline's members never appear beside it for the same requirement; a named skill that is missing is a `skip`, never stood in for by another skill or by the session's own work; only work no skill covers becomes a session step.
  - **Restraint.** Every step serves a named requirement; one that serves none is cut, a single skill stays a single action, and an added check is never a second action or a second check on the same output.
  - **Clean versions and generic examples.** Rewriting an edited artifact as if it had always said so, and keeping a durable document's examples generic rather than real numbers and names, are checks the writing skill and the `sip` after it run on the output, so the router adds no step for them.
- Never select `re0-workflow` itself or its alias `paperthin` as a step; the alias only forwards here, so either would loop.
- The router writes nothing of its own: no plan file, log or record, in the repository or outside it. Every write comes from a run step's own skill under that skill's contract, or from a session step the shown plan names.
- Destructive or irreversible means deleting, pushing, force-pushing, publishing, tagging, sending a message to someone, or spending money. Such a step is a `user-handoff` even when its skill is model-invoked or the session could do it.
- Never run a user-only skill, and never drop an installed one to make the order runnable; it stays in the graph as a `user-handoff`. A step the router cannot run is a `user-handoff` or a `skip`, never a silent recommendation, and a skip never counts as success.
- `nba`, a sibling that reads live project state and names one next action, runs nothing; this skill orders and runs a graph for one stated intent.
- `sip` runs its own fixed set of checks on newly changed output; it is one node, never reproduced member by member.

## Verification

Before running the first step, and again before the final report:

1. Every selected target's trigger, output, installation, invocation lane and authority were read from its own contract.
2. The intent was read through readback, or the reason it was not is stated, and nothing but that read happened before the plan was shown.
3. The plan check exited 0 before the plan was shown, and the report check before the report was given; nothing was written to disk. The script decides the structure (readback never a step, run order, every requirement traced, one stop condition, no cycle and a reject in run order, typing, one closing `sip` per stretch that writes, one outside read only for a judgment no `sip` tastes, approval before any run write); whether a step truly serves its requirement stays the router's read.
4. Every installed user-only, destructive or decision step is a `user-handoff` with the exact invocation or the question, and what to bring back, never `invoke-model-skill`; every `session-step` is work no installed skill covers.
5. The graph was shown before anything ran, and approval was asked once when a step to run writes.
6. Each run step's expected output was checked before the next step started, the run stopped at the first `user-handoff` or failure, and nothing ran past the last shown step.
7. The report gives each step's outcome, every requirement's status, and whether the stop condition was reached or at which step the run stopped early; a no-match says the goal was not done.
