Use when someone states a goal but does not know which skills serve it or in what order, asks which skills to use, or wants a job that needs several skills run end to end. Typing /paperthin lands here."
---

Turn one stated intent into an ordered skill graph, show it, and run the steps the session may run.

## Goal

Someone who does not know this suite's catalog says what they want and sees every part of it done, nothing misread or dropped: the request read into requirements, the installed skills that serve them ordered and shown before anything runs, the session's steps run, and a stop at the first step that needs the human, with a report of every step and requirement.

## Workflow

1. Read `readback`'s SKILL.md first, when installed, then the human's stated intent and the installed roster from the host catalog or skill directories. If given only live state without a stated intent, ask for the intent rather than infer it. Read, once and before any verdict, the contract and invocation lane of each skill whose description could serve the request, and of `sip` and the outside reads steps 4 and 5 may add. Once a verdict is reached (a plan, a no-match or a cycle), no tool call reads or searches anything more. Open nothing a planned step will read (a draft, a file it edits, data it fetches): opening it is running that step before approval. `disable-model-invocation: true` in a SKILL.md, or `policy.allow_implicit_invocation: false` in its `agents/openai.yaml`, means user-only, and so does a disagreement between them; otherwise the skill is model-invoked.
2. Re-read every request before choosing anything, applying `readback`'s method yourself and never invoking it: restate the request in your own words and check the restatement against the request and the contracts step 1 read. When two readings survive that they cannot settle, the reply holds only the restatement and one specific question, and no plan is built until the human answers; the question is no action. Decompose the confirmed read into numbered requirements (`r1`, `r2`, ...), one per thing asked, in the human's order, and one line beginning `understood as: `. The read opens the reply that shows the plan, on every request, and is no step, action or tool call. Skip the restatement only when the intent names one installed skill and its one target and asks nothing else (`single-named-step`); the requirement and the line are still written. Without readback installed, restate the request the same way and say the read went unchecked.
3. A named skill the roster lacks is first of all not installed: the plan and the reply say so before anything else about it, no invocation string for it appears anywhere, it stays a `skip` step, and installing it is the human's choice; when it is the only one, the reply reports it as not installed, without a plan. For each requirement, select the installed skills whose triggers and outputs serve it. Add no step the requirements do not need and no orientation skill; when one skill suffices, use one node and say ordering is trivial. Work no skill covers becomes a step of its own, typed by the table in step 7, only inside a plan with at least one skill step. A requirement nothing installed serves and no one present could authorize is unmet, with the reason. A request no installed skill serves at all is a no-match, whatever the session could do itself; a no-match and a cycle (step 6) make no tool call after the contract reads, and the reply, written from what was read, gives the read of step 2, then says plainly that the goal was not done and why.
4. Close each stretch of the run that writes composed content with one `sip` step, the suite's taste test for new output, run as one node. A write that only places text the human gave verbatim, or makes an edit a skill fully decides (a reorder, a rename), is marked `fixed` and gets none. A stretch ends before each step whose first (expected) type is `user-handoff`; the human's write there belongs to the stretch after it. The stretch's `sip` follows every write in it, and a stretch that writes nothing gets none. A pipeline that runs `sip` itself closes its own writes. A pass its contract runs last in a sequence of rewriting passes is marked `runs_last`: the stretch's `sip` goes before it, and nothing follows it. List the checks the closing `sip`'s contract runs under its node as its members, each with its contract's condition, so no call it makes is unshown. It writes too (its cleanup pass edits the changed docs), under the same approval, and no `sip` follows it. It runs when any write it covers ran and is skipped only when all of them were. Not installed, it is a plain `skip` with no members and `"writes": false`. A closing `sip` that is skipped or missing while a write it covers ran leaves the stop condition unreached, and the report says that output went untasted. A fix it proposes goes into a revised plan, shown and approved before it runs.
5. A judgment the run delivers (a verdict or a choice with no file) is tasted by a running `sip` after it in the same stretch. When none follows it, add one outside read after it: `shower` for whether it reads clearly to someone with no context, `factchk` for claims about the world, or `mandela` for an eval, metric or experiment. A judgment that is itself one of those reads gets none. An added check serves the requirements of the steps it checks, is shown with its reason, and is no action; when its skill is not installed it stays as a `skip`, and the report says the output it would have checked went untasted.
6. Order the steps by their contracts' prerequisites: a step depends on another when its firing precondition needs that step's output, and each ordering reason cites that prerequisite, never an invented one. Every prerequisite a contract states is an edge, and none is dropped to make the order runnable. List the steps in run order, the session's steps before a handoff where the prerequisites allow, so the run reaches the human once and late. Find cycles from the requires-edges before showing anything. A cycle makes the result a `reject`, named along its requires-edges, each step followed by one whose output it needs (`skill-a requires skill-b requires skill-a`), with no steps. Otherwise give the graph one observable stop condition that shows the goal met rather than a step merely returning (a ready verdict, not a report that finds problems): every requirement was served or no longer applies.
7. Give every step the fields of the plan shape in step 9: its target is the skill that acts, the work no skill covers, or the question for a human decision, and its expected output is what the skill's own contract promises. A step writes when it creates or changes a file's content, and a contract silent on writing counts as writing; an unreadable lane counts as user-only. A commit or a history rewrite changes a record without new content, so it is marked `vcs`: it needs approval like a write, and no `sip` tastes it. A frozen pipeline, a skill whose own contract runs a fixed sequence of other skills, is one node whose members are the skills it runs itself, and it writes when a member writes; a skill it only hands to the human is no member. Type each step by the first row below that applies. A step whose type depends on an earlier result lists the types it can take, the expected one first, with the condition that decides. Once that result exists the step is typed, and another type than the expected one re-plans the rest, drawing its stretches anew, checked and shown again before it runs.

   | Type | Meaning and precondition | Cost owner |
   | --- | --- | --- |
   | `skip` | The step does not run: its skill is not installed, its condition does not apply, or no one present can grant the authority it needs. A step that depends on it is skipped too, its reason naming the step it lost. | None. |
   | `user-handoff` | The human acts: the target is user-only or a pipeline with a user-only member (on lane `user`, its user-only members listed); the step is destructive or irreversible (deleting, pushing, force-pushing, publishing, tagging, sending a message to someone, spending money), even when its skill is model-invoked or the session could do it; it is a decision; or it needs authority the human holds and the session does not. | The human's time, at their discretion. |
   | `invoke-model-skill` | The router runs it: the target is an installed model-invoked skill, the session holds authority for it, and it is neither destructive nor irreversible. | This run's budget. |
   | `session-step` | The session does it: no skill covers the work, the session holds authority for it, and it is neither destructive nor irreversible. | This run's budget. |

8. For each `user-handoff`, say what the human does and what result to bring back. For a skill, give the exact invocation in the host's syntax with the installed name. For a decision, give the question and the answers that change the next step. When the host's syntax is unknown, the handoff holds that question, asked when the plan is shown, instead of a command.
9. A request for the order alone makes no script call: its reply shows the plan without JSON, each step's fields from the shape below in a compact table, the skippable condition and cost owner included, adds nothing the requirements and contracts do not call for, and ends. Check any other plan before it is shown by piping it as JSON straight into `node <skill>/scripts/plan.mjs -`, `<skill>` being the folder that holds this SKILL.md, never through a file: in a POSIX shell end the command with `<<'EOF'`, then the JSON, then a line holding `EOF`; in PowerShell pipe a here-string, `@'`, the JSON, `'@ | node <skill>/scripts/plan.mjs -`. Exit 0 passes; exit 1 names each broken rule, fixed and checked again; exit 2 is a usage error, invalid JSON or an empty stdin. `--json` prints the problems as JSON, and `--help` lists every rule the script decides. Never show a plan the script refused. The plan has this shape:

   ```json
   {
     "readback": "applied",
     "understood_as": "understood as: <the confirmed read>",
     "requirements": [{ "id": "r1", "text": "<one thing asked>" }, { "id": "r2", "text": "<another>", "unmet": "<missing-skill> is not installed" }],
     "steps": [
       { "id": "s1", "target": "<skill>", "predecessors": [], "serves": ["r1"], "type": "invoke-model-skill", "precondition": "<when it fires>", "output": "<what its contract returns>", "skippable": "<when it may be skipped>", "cost_owner": "run", "writes": true, "lane": "model" },
       { "id": "s3", "target": "<missing-skill>", "predecessors": [], "serves": ["r2"], "type": "skip", "reason": "<missing-skill> is not installed", "precondition": "<when it would fire>", "output": "<what its contract would return>", "skippable": "always: it is not installed", "cost_owner": "none", "writes": false, "lane": "missing" },
       { "id": "s2", "target": "sip", "added": "sip", "members": ["shower", "factchk", "mandela", "ssotize", "detool", "re0"], "predecessors": ["s1"], "serves": ["r1"], "type": "invoke-model-skill", "precondition": "s1 wrote its output", "output": "findings on that output and its cleanup edits", "skippable": "when s1 wrote nothing", "cost_owner": "run", "writes": true, "lane": "model" }
     ],
     "stop": "<the one observable stop condition>"
   }
   ```

   `readback` is `applied`, `single-named-step` or `missing`. `type` is one type, or the list a conditional step can take with the expected type first; `cost_owner` is `none`, `human` or `run` by the table, for a conditional step that of its first type; `lane` is `model`, `user` or `missing` for a skill and `none` for work or a question no skill takes. A skip adds `reason`; a handoff adds `handoff` and `bring_back`; a frozen pipeline or the closing `sip` adds `members`, and `user_members` for those that are user-only; a commit or rewrite adds `"vcs": true`; a write from step 4 that needs no taste adds `"fixed": true`, and a pass that runs last `"runs_last": true`; a destructive or irreversible step adds `"destructive": true`; a delivered judgment adds `"judgment_only": true` and never writes; a check from steps 4 and 5 adds `"added": "sip"` or `"added": "outside-read"`.
10. Before any step runs, show the requirements and the `understood as:` line, one line naming exactly the calls made to build the plan (each contract read and each check run), never that nothing ran, then the graph in run order: every field of every step, why each sits where it does, the number of actions, each added check under the steps it closes with its reason, the stop condition, and any question step 8 holds. When any step the session runs (`invoke-model-skill` or `session-step`) writes or is `vcs`, wherever it sits, ask once, now, for approval of the shown plan; until it is given, the report stands under approval `pending`, checked by one `--report` call, every step waiting except a `skip`, which is `skipped` with its reason. The approval covers every write the plan shows, across a resume, until it changes. It grants no authority a step lacked, so it never turns a `user-handoff` into a run step. When no step the session runs writes or is `vcs`, run right after showing the plan under approval `not-needed`. When the human edits the plan, order, check and show it again before running.
11. Run in order. For each `invoke-model-skill` step, call the Skill tool with its target once, passing the intent and its predecessors' outputs; on a host without one, follow the skill's SKILL.md and say so. Do each `session-step` yourself, once, within what the shown plan says. Before starting the next step, check its expected output: the file or record exists, or the skill's own report states the result. A step that does not produce its expected output failed, and the run stops there. When a produced output breaks a later step's precondition, that later step and its dependents become `skip` steps with the reason, the closing `sip` apart (step 4), and the run goes on with the steps that do not depend on them.
12. Stop at the first `user-handoff` or failure, or at the end, and give the report in the conversation, the state a resume reads. The report is the shown plan with each step's outcome, result and status merged in by id, checked with `node <skill>/scripts/plan.mjs - --report` before it is given:

   ```json
   {
     "readback": "applied",
     "understood_as": "understood as: <the confirmed read>",
     "approval": "not-needed",
     "stop_reached": true,
     "requirements": [{ "id": "r1", "text": "<one thing asked>", "status": "served" }],
     "steps": [
       { "id": "s1", "target": "<skill>", "predecessors": [], "serves": ["r1"], "type": "invoke-model-skill", "precondition": "<when it fires>", "output": "<what its contract returns>", "skippable": "<when it may be skipped>", "cost_owner": "run", "writes": false, "lane": "model", "outcome": "ran", "result": "<what it produced>" }
     ],
     "stop": "<the one observable stop condition>"
   }
   ```

   `approval` is `approved`, `not-needed` or `pending` (step 10). A step's `outcome` is `ran`, `returned` (a handoff whose result came back), `skipped`, `handed-off` (the handoff the run stopped at), `failed`, or `waiting` (every step after the stop or not yet reached), and its `result` says what it produced or why, unless it waits; a check's `result` names the parts its own report skipped, never calling it clean. A requirement's `status` is `served`, `handed-off`, `waiting`, `skipped` (it no longer applies) or `unmet`, the last two with a `reason`. `stop_reached` is true only when nothing waits, stopped or is unmet and every write that ran was tasted; when a skipped or missing step's output is one the stop condition needs, the report says the run ended with it unmet. The report also holds the handoff with what to bring back. When the human returns with the result in the same conversation, a new invocation checks it against the handoff step's expected output: a match makes that step `returned` and the run goes on under the same approval, while a changed or failed result re-plans from that step, checked and shown again before running. Without the report, start again from step 1.

## Rules

- The plan carries the suite's working rules: the result never rests on its author (steps 4, 5, 9), one owner per job (steps 3, 7 and the rule on missing skills), restraint (steps 3 to 5).
- Never select `re0-workflow` itself or its alias `paperthin` as a step; the alias only forwards here, so either would loop.
- The router writes nothing of its own, a temporary file included: no plan file, log or record, in the repository or outside it. Every write comes from a run step's own skill under that skill's contract, or from a session step the shown plan names, and a report names every file the run wrote.
- Never drop an installed user-only skill to make the order runnable. A step the router cannot run is a `user-handoff` or a `skip`, never a silent recommendation, and a skip never counts as success.
- A missing or failed skill is never replaced, by another skill or by the session's own work, and a planned skill's work is never done by hand or by an ad hoc script, before or after approval: its step invokes it.
- `nba` names one next action from live state and runs nothing; this skill runs a graph for one stated intent.

## Verification

Unless the result is a no-match, a reject (step 3) or an order alone, check before running the first step and again before the final report:

1. Every selected target's trigger, output, installation, lane and authority were read from its contract in step 1, nothing a planned step reads was opened, readback's method was applied with no readback call, and the build line names every call made before the plan was shown.
2. The plan was checked before it was shown, and each report before it was given. The script decides the rules its `--help` lists; whether a step serves its requirement and whether writes and judgments are marked honestly was read.
3. Every step's type follows the table in step 7, and every prerequisite a selected contract states is an edge of the plan; a plan the check passes with a contract edge missing is a router defect.
4. The plan was shown before anything ran, approval was asked once where step 10 needs it, each run step's output was checked before the next step started, and the run stopped at the first `user-handoff` or failure with nothing, no check included, past the last shown step.
5. The report is the one step 12 describes.
