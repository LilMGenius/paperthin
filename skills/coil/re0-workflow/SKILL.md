Read one stated intent back into requirements, turn them into a checked skill graph, show it, and run the steps the session may run.

## Goal

Someone who does not know this suite's catalog should be able to say what they want and see every part of it done, with nothing misread or dropped. Read the intent back into numbered requirements, select and order the installed skills that serve each one, check the plan with the bundled script, show it before anything runs, run each step the session holds authority for, doing itself the work no installed skill covers, stop at the first step that needs the human, and end by reconciling every requirement. The plan carries the suite's working rules as decisions (under Rules), so a run keeps them without anyone asking.

## Workflow

1. Read the human's stated intent and the installed roster from the host catalog or skill directories. If given only live state without a stated intent, ask for the intent rather than infer it. Read each candidate's contract and invocation lane: `disable-model-invocation: true` in its SKILL.md, or `policy.allow_implicit_invocation: false` in its `agents/openai.yaml`, means user-only; otherwise it is model-invoked, and when the two files disagree it is user-only.
2. Read the intent back before choosing anything: call the Skill tool with "readback" on the intent as the human wrote it, and wait for the answer to any question it asks. Turn the confirmed read into numbered requirements (`r1`, `r2`, ...), one per thing the human asked for, in their order, each part of a bundled request its own item, plus one line beginning `understood as: `. The readback is the plan's first step, and every other step follows it. Skip it only when the intent names one installed skill and its one target and asks nothing else, and record `single-named-step` as the reason: a single named invocation leaves nothing to misread, and anything more is read back. When readback is not installed, keep its step as a `skip` with that reason, restate the intent into requirements yourself, and say the read went unchecked; reading the intent is this router's own job, so this is the one missing skill it stands in for, and the steps after it still run.
3. For each requirement, select only installed skills whose triggers and outputs serve it, deciding by the Rules below, and record which requirements each step serves. A frozen pipeline (a skill whose own contract runs a fixed sequence of other skills) that already serves a requirement is one node, never expanded; read its members only to type it, so the node counts as writing when any member writes and is a `user-handoff` when any member is user-only, and record them as its members. After every step that writes, whoever performs it (a skill, the session or the human), add a `sip` step (the suite's taste test for new output) on that step's output, unless the step's members already include it; after a human's step it runs once the result comes back. Mark a run step whose result rests only on the session's own judgment (a verdict, a choice, a plan with no file to taste) as judgment-only and add an outside read after it: `shower` when the question is whether it reads clearly to someone with no context, `factchk` when it asserts claims about the world, `mandela` when it is an eval, metric or experiment; a `sip` step after it counts, since it runs that cold read. An added check step serves the requirements of the step it checks. Work a requirement needs that no installed skill covers and no one named a skill for (a local rebase, writing a check) is a step of its own, typed by the table below. A skill the intent or a selected contract names that the roster lacks stays as a `skip` step, never replaced, and a requirement only such steps serve is recorded as unmet with the reason. Do not pad the graph, require an orientation skill, invent a pipeline skill, or substitute another skill for a missing one; if one skill suffices, use exactly one node and say ordering is trivial.
4. Order the steps by their contracts' prerequisites: a step depends on another when its firing precondition needs that step's output, and every step depends on the readback. Detect cycles before showing the graph; if one exists, the whole result is a `reject` naming the cycle, such as `skill-a -> skill-b -> skill-a`, with no steps past the readback and no partial order. List the steps in run order, each after its predecessors, and where the prerequisites leave the order free put the session's own steps before a handoff, so the run reaches the human once and as late as it can. Give the graph one observable stop condition, the state that means every requirement was served; a graph with nothing past the readback, or a `reject`, ends at its own report.
5. Give every step an identifier, a target (the skill that acts, the work when no skill covers it, or the question when the step is a human decision), predecessor identifiers, the requirements it serves, exactly one type, firing precondition, expected output (for a skill, limited to its own contract), skippable condition, cost owner, its target's lane, and whether it writes: creates or changes content (a file, document, record or message), where moving content that already exists (a push, a tag, a publish) does not count. Assign its type by the first row below that applies, so a missing user-only skill is a `skip`. Where a contract does not say whether its skill writes, count it as writing; where its lane cannot be read, count it as user-only. A step whose type depends on a predecessor's output is shown as conditional with the types it can take, and typed once that output exists.

   | Type | Meaning and precondition | Cost owner |
   | --- | --- | --- |
   | `skip` | The step does not run, and the graph goes on without it: condition not applicable, skill not installed, or no authority that anyone present could grant. A step that depends on it is skipped too, with the same reason, except after a missing readback (step 2). | None. |
   | `user-handoff` | The human acts: the target is user-only, the step is destructive or irreversible, a human decision is needed, or the work needs authority the human holds and the session does not. | The human's time, at their discretion. |
   | `invoke-model-skill` | The router runs it: none of the rows above applies, so the target is installed and model-invoked, the session already holds authority for the work, and the step is neither destructive nor irreversible. | This run's budget. |
   | `session-step` | The session does the work itself: no row above applies because no skill covers it, the session holds authority for it, and it is neither destructive nor irreversible. Destructive or irreversible work (a push, a tag, a publish, a delete, a message sent) stays a `user-handoff`. | This run's budget. |
   | `reject` | Not a step: the whole result when the request cannot be served as a graph, naming the cycle when cyclic. | None. |

6. For each `user-handoff`, say what the human does and what result to bring back: for a skill, the exact invocation they type, in the host's syntax with the installed name (a destructive step whose skill is model-invoked is still typed by the human); for a decision, the question and the answers that change the next step. If the host's invocation syntax is unknown, ask for it now, before the plan is written, instead of inventing it.
7. Write the plan as JSON to a file outside the repository being worked on (the OS temp directory unless the human names a place), and check it with `node <skill>/scripts/plan.mjs <plan-file>`, `<skill>` being the folder that holds this SKILL.md: exit 0 means every invariant holds; exit 1 names each broken one, which is fixed in the plan and checked again; exit 2 is a usage error or unreadable JSON; `--json` prints the problems as JSON. Never show a plan the script refused. The file has this shape:

   ```json
   {
     "intent": "<the human's words>",
     "understood_as": "understood as: <the confirmed read>",
     "requirements": [{ "id": "r1", "text": "<one thing asked>" }, { "id": "r2", "text": "<another>", "unmet": "<why nothing installed serves it>" }],
     "steps": [
       { "id": "s1", "target": "readback", "predecessors": [], "serves": [], "type": "invoke-model-skill", "precondition": "<when it fires>", "output": "<what its contract returns>", "skippable": "<when it may be skipped>", "cost_owner": "run", "writes": false, "lane": "model" },
       { "id": "s2", "target": "<skill>", "predecessors": ["s1"], "serves": ["r1"], "type": "invoke-model-skill", "precondition": "<when it fires>", "output": "<what its contract returns>", "skippable": "<when it may be skipped>", "cost_owner": "run", "writes": false, "lane": "model" }
     ],
     "stop": "<the one observable stop condition>"
   }
   ```

   `type` is one type, or the list a conditional step can take with the expected type first; `cost_owner` is `none`, `human` or `run` by the table, for a conditional step that of its first type; `lane` is `model`, `user` or `missing` for a skill, and `none` for work or a question no skill takes. A skip adds `reason`; a handoff adds `handoff` (the invocation or question) and `bring_back`; a frozen pipeline adds `members`; a destructive or irreversible step adds `"destructive": true`; a judgment-only step adds `"judgment_only": true`. A skipped readback is `"readback_skip": "single-named-step"` with no readback step, and a cyclic request is `"reject": "<the cycle>"` with no `stop`.
8. Before any step runs, show the requirements, the `understood as:` line, the whole typed graph in order with every field of every step, why each step sits where it does, and the stop condition. If the human asked only for the order, stop here: the checked plan file is the result, nothing runs, and no report check is owed. If any `invoke-model-skill` or `session-step` step anywhere in the graph, before or after a handoff, writes, ask once, now, for approval of the shown plan. That approval accepts the plan and every write it shows, across a resume, until the plan changes; it grants no authority a step lacked, so it never turns a `user-handoff` into a run step. If no step to run writes, run right after showing the plan. If the human edits the plan, order it again, check it again, and show it again before running.
9. Run in order. The readback already ran in step 2 and is recorded as `ran` without a second call. For each other `invoke-model-skill` step, call the Skill tool with that step's target, once for that step, passing the intent, the requirements it serves and its predecessors' outputs; on a host with no Skill tool, run the skill the way that host does (reading its SKILL.md and following it counts) and say so. Do each `session-step` yourself, once, within what the shown plan says. Before starting the next step, check its expected output: the file or record exists, or the skill's own report states the result. If a step does not produce its expected output, it failed and the run stops there. If a step's output, though produced, breaks a later step's precondition, mark that later step and its dependents `skip` with the reason and go on with the steps that do not depend on it. Never retry by swapping in another skill.
10. Stop at the first `user-handoff` or failure. Record in the plan file each step's `outcome` with a `result` saying what it produced or why: `ran` (the router or the session ran it), `returned` (a handoff whose result came back), `skipped` (typed skip, or skipped by step 9), `handed-off` (the handoff the run stopped at), `failed` (the step the run stopped at for a missing output), or `waiting` (every step behind the stop, not reached yet, which needs no result). Record each requirement's `status`: `served` when a step serving it ran and none is still open, `handed-off` when one of its steps is the handoff, `waiting` when its steps wait behind the stop, `skipped` when it no longer applies, or `unmet` when nothing installed or nothing that ran served it, the last two with a `reason`. Set `stop_reached` to true or false, then check it with `node <skill>/scripts/plan.mjs <plan-file> --report`. That file is the state a resume reads. When the human returns with the handoff's result in the same conversation, a new invocation reads the file and checks the result against the handoff step's expected output: a match makes that step `returned` and the run goes on from the next step under the same approval, while a changed or failed result re-plans from that step, then checks and shows the new graph before running. The readback recorded in the file stands; if the file is out of reach, start again from step 1.
11. End with the report: every requirement reconciled as served, handed off, waiting, skipped with its reason, or unmet; every step's outcome; and whether the stop condition was reached or the run stopped early at a named step. Check the final file with `--report` before reporting. A requirement left unmet means the stop condition was not reached.

## Rules

- The plan makes these decisions on every run, from the suite's working rules:
  - **The result never rests on its author.** The session that made an output judges it worst, so a write is followed by `sip` and a judgment-only step by an outside read (step 3), and the router's own plan is checked by the bundled script, never by rereading it.
  - **One owner per job.** A step that would redo what an installed skill already owns is replaced by that skill; a frozen pipeline's members never appear beside it for the same requirement; a named skill that is missing is a `skip`, never stood in for by another skill or by the router's own work, readback aside (step 2); only work no skill covers becomes a session step.
  - **Restraint.** Every step past the readback serves a named requirement; one that serves none is cut, and the graph is never padded to look thorough.
  - **Clean versions and generic examples.** Rewriting an edited artifact as if it had always said so, and keeping a durable document's examples generic rather than real numbers and names, are checks the writing skill and the `sip` pass after it run on the output, so the router adds no step for them.
- Never select `re0-workflow` itself or its alias `paperthin` as a step; the alias only forwards here, so either would loop.
- The router writes only its plan file; every other write comes from a run step's own skill under that skill's contract, or from a session step the shown plan names.
- Destructive or irreversible means deleting, pushing, force-pushing, rewriting shared history, publishing, tagging, sending a message to someone, or spending money. Such a step is a `user-handoff` even when its skill is model-invoked or the session could do it.
- Never run a user-only skill, and never drop an installed one to make the order runnable; it stays in the graph as a `user-handoff`. A step the router cannot run is a `user-handoff` or a `skip`, never a silent recommendation, and a skip never counts as success.
- `nba`, a sibling that reads live project state and names one next action, runs nothing; this skill orders and runs a graph for one stated intent.
- `sip` runs its own fixed set of checks on newly changed output; it is one node, never reproduced member by member.

## Verification

Before showing the plan, and again before the final report:

1. Every selected target's trigger, output, installation, invocation lane and authority were read from its own contract.
2. The readback ran first, or the plan records why it was skipped, and the `understood as:` line and requirements came from it.
3. `plan.mjs` exited 0 on the plan before it was shown, and with `--report` on the file the final report reads. The script decides the structure (readback first, run order, every requirement traced, one stop condition, no cycle, typing, `sip` after every write, an outside read after judgment); whether a step truly serves its requirement, and whether a judgment-only step was marked honestly, stays the router's read.
4. Every installed user-only, destructive or decision step is a `user-handoff` with the exact invocation or the question, and what to bring back, never `invoke-model-skill`; every `session-step` is work no installed skill covers, neither destructive nor irreversible.
5. The graph was shown before anything ran, and approval was asked once when a step to run writes.
6. Each run step's expected output was checked before the next step started, the readback was not called twice, and the run stopped at the first `user-handoff` or failure.
7. The report reconciles every requirement and says whether the stop condition was reached or at which step the run stopped early.
