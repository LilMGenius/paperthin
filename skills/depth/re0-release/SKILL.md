Ship a release of the repository this runs in, in one deliberate command: check a pending change against the repository's release procedure, commit it, then tag and publish once confirmed.

## Goal

A release lands complete and trustworthy: the repository's own procedure met, every manifest version bumped by the kind of change, a commit message that hands off without the diff, release notes in house style carried as the signed tag's message, and a published artifact the release workflow produced on its own where the repository has one. `re0-release` walks a pending change down that path. It calls `sip` when installed, applies commit-economy directly, and never calls another user-invoked skill. Every step that commits or writes in public waits for its own approval: the first confirmation shows the whole proposal and allows a local commit, the second allows the tag and the publish, and a re-cut tag or a comment on a contribution each ask again. The run goes no further than the human has approved.

It is **user-invoked**: shipping is a deliberate human action, so only the human runs it, once they have decided to ship.

## Workflow

1. **Read the procedure.** Find the repository's own release procedure: the Shipping and Releasing sections of its root `AGENTS.md`, else its `CONTRIBUTING.md`, else none. Check the pending diff against every item it states except the bump and the `sip` run, which steps 2 to 4 own, and report any gap and stop rather than guess past it. With no written procedure, say so and go on. Then read the diff for anything that is not this one release (an unrelated concern, a file another author or agent staged): propose the split or the exclusion and wait for the answer before anything below is drafted. Every file named below that the repository lacks is skipped.
2. **Classify the bump** once every open question that bears on what ships is answered (a missing behavior obligation, a contract question, the split); until then, report the question and name no version. A new skill is minor; a fix or docs-only change is patch; a skill removed with no replacement path is major. Classify an existing skill's enhancement by kind, not size, against its own prior spec: wrong behavior is a fix (patch, including new plumbing that serves only the fix); correct but narrower, or missing a dimension, is a new capability a user newly reaches for (minor). State which case applies, not just the bump. The notes follow the case: only a minor or major release carries a `### New` section (step 6).
3. **Taste-test.** Call the Skill tool with "sip"; on a host with no Skill tool, read `sip`'s `SKILL.md` and follow it. Apply its findings, except one that needs an approval (an `ssotize` consolidation plan, say), which joins the step 8 proposal instead. When `sip` is not installed, say so and skip this step. Either way, keep for step 8 whether it ran, what it found and what it changed.
4. **Bump and run the checks.** Set the new version in every manifest that carries it, to the same value: `package.json`, its lockfile, and plugin manifests such as `.claude-plugin/plugin.json`, where present. Then run the repository's own check and test commands (in this repository, `npm test` and `npm run check`) and keep their result for step 8; fix a failure before the proposal goes out.
5. **Draft the commit message** to commit-economy from the first draft: one bullet per real, durable change, supporting edits folded in; nothing the diff or version already proves; no co-author tag except a closing `Co-authored-by` trailer that credits a human contributor on a squashed or carried contribution. Match the local log's shape, or, absent one, a subject plus one `-` bullet per change on a single unwrapped line. Rewrite the message as edits develop instead of appending to it. If an existing commit needs cleanup, tell the human to run `/re0-git`; it is user-invoked, so never call it.
6. **Write the release notes** to `.re0/release/RELEASE_NOTES.local.md`, gitignored local scratch that becomes the signed tag's message and never ships as a file. This is the house style; `scripts/notes.mjs` decides each rule marked *(checked)*, and you decide each marked *(judgment)*:
   - one `##` heading with no version number (`X.Y.Z`) in it *(checked)*, naming the release's durable idea *(judgment)*;
   - one paragraph on one line after the heading *(checked)*, short and present-tense, saying what is true now *(judgment)*;
   - sections in this order, each at most once: one New section (`### New` or `### New: <label>`), `### Also`, `### The catalog (N skills)` (`(1 skill)` for one), and `### Install` *(checked)*; only the sections the release earns, the catalog only when the roster needs re-mapping *(judgment)*;
   - `### New` holds only new capabilities a user reaches for, so it appears only in a minor or major release; a fix or tightening of an existing skill goes under `### Also` *(judgment)*;
   - `### Also` holds only what New does not already say, so a release with a single change carries that one section and Install: an Also bullet that leads with a New bullet's subject fails *(checked)*, and any other repeat is *(judgment)*;
   - every section but Install holds single-line `-` bullets and nothing else, no lead sentence *(checked)*;
   - each New bullet opens with a bold lead *(checked)* that is the skill's name (`` **`name`** ``) or a short label (`**One command.**`), never a whole sentence *(judgment)*;
   - each catalog bullet names a perspective and its skills, plain (`` - `depth/`: `re0`, `shower` ``) or with the perspective bold and described (`` - **`depth/`** (one artifact): `re0` ``), and together they list the N skills the heading counts, each once *(checked)*, which are the real roster *(judgment)*;
   - `### Install` is the last section and not empty *(checked)*. Where `.agents/install-block.md` holds a `release-notes` block, Install is the contents of its markdown fence without the fence lines, or of the `release-notes-0.x` block for a 0.x tag *(checked)*; otherwise it carries the install commands the repository documents (its README's install section) verbatim *(judgment)*;
   - each externally contributed change is credited inline with its PR number and author handle, `(#123, @handle)`, a run of pull requests as `(#123-#125, @handle)`, and each co-author as one more `, @handle` before the closing parenthesis, and no other `#` number appears outside code, link targets and URLs *(checked)*; every external change carries its credit *(judgment)*;
   - every claim about a skill stays inside what that skill's `SKILL.md` says it does, never wider *(judgment)*;
   - skill names and paths in backticks *(judgment)*, and no em dash *(checked)*;
   - nothing the tag or version already proves *(judgment)*.
7. **Check the notes.** From anywhere in the repository, run this skill's script on them: `node <this skill's folder>/scripts/notes.mjs .re0/release/RELEASE_NOTES.local.md` (in this repository, the folder is `skills/depth/re0-release`). Its root is the git top level, or the current folder outside git, unless `--root` names one. Where an install block exists, the version picks its era: `--version X.Y.Z`, else `--tag vX.Y.Z` (which checks that tag's message instead of a file), else a `vX.Y.Z.md` file name, else `package.json`.
   - Exit 0: every *(checked)* rule holds. In a repository with no install block, or none for the note's era, the output says Install was not checked against a block; that is a pass, and the *(judgment)* rule on Install covers it.
   - Exit 1 names each failure by line: fix the notes, except an `install-block` failure (line 0), which is fixed in `.agents/install-block.md` because its `release-notes` block has drifted from the route blocks.
   - Exit 2: the check could not run. It was a usage error, `--tag` outside a git repository, or a file it needs that is missing or unreadable (the notes, the install block, or `package.json` when the block needs a version). Fix that and run it again.
   - Then read the notes against every step 6 rule marked *(judgment)* and write a verdict for each.
   - The check gates only the note being written; earlier tags stay as they are (Rules).
8. **First confirmation.** Show the human the whole proposal: step 1's result; the files the commit carries and any split step 1 settled; whether `sip` ran, what it found, what it changed and any finding that waits for approval; the bump with its case and every manifest it sets; step 4's check and test results; the commit message; the release notes with step 7's exit and each judgment verdict; and the tag it would cut, `vX.Y.Z`. On explicit approval, apply any approved `sip` finding, then commit; the commit stays local. This approval covers the proposal and the local commit only, whatever else it names. When the human stops there, end the run by reporting what remains (steps 9 to 12) and that the notes wait in `.re0/release/RELEASE_NOTES.local.md`.
9. **Second confirmation, then land and tag.** Ask the human, as its own question, to land the commit and publish, naming the path below that applies and the tag. On approval, read the default branch's rules with `gh api repos/<owner>/<repo>/rules/branches/<branch>`.
   - Where they require a pull request, push the commit as its own branch, open a pull request titled with the commit's subject, wait for its required checks, and squash-merge it. Fetch, and confirm that `origin/<branch>`'s tree equals the approved commit's tree (`git rev-parse origin/<branch>^{tree}` against `<commit>^{tree}`); a difference stops the run. The tag goes on the commit that landed.
   - Otherwise push the branch. The tag goes on the approved commit.
   - Sign the tag with `git tag -s vX.Y.Z <commit> -F .re0/release/RELEASE_NOTES.local.md --cleanup=verbatim`, confirm `git tag -v vX.Y.Z` reports a good signature, and push the tag. Report which path ran.
10. **Watch the workflow**, where the repository has one. Follow the run the pushed tag triggered to completion and report success or the actual failure; never assume it landed. `gh run list --workflow <file> --branch vX.Y.Z` finds the run, `gh run watch <run-id> --exit-status` follows it, and `gh release view vX.Y.Z --json body,isDraft` must show the notes with `isDraft` false. A failure whose cause lies outside the tagged commit is fixed and rerun (`gh run rerun <run-id> --failed`). Once the run succeeded, compare the Release body with the tag's message without its signature block and trailing whitespace. A mismatch is fixed by rerunning the workflow (`gh run rerun <run-id>`), never by editing the body, and reported; it does not hold up steps 11 and 12.
   - A tag cut wrong (its message, signature or target) is deleted and re-cut at the same version; the version moves on only when a published artifact is wrong. A re-cut for the signature or the target keeps the message byte-identical: write the old message, signature block removed, to a file and sign the new tag from it with `-F <file> --cleanup=verbatim`. Only a re-cut for the message itself carries new notes, and those pass step 7.
   - The workflow file at the tagged commit is the one a re-pushed tag runs, so read it before a re-cut. A re-cut is a public write: show the human the tag, the cause and the notes it will carry, and re-cut only on their approval.
11. **Close out contributions.** After confirmed success, close each external contribution the release landed: whoever reviewed it approves the PR, then closes it with a comment carrying the release notes' credit. A contribution squashed or rebuilt into the release is closed, not merged, so the approval records acceptance rather than rejection. Any collaborator or maintainer with review access may do this. Approving, closing and commenting are public writes: show the human each comment and post it only on their approval.
12. **Retire the cycle**, only after the release workflow succeeded. Move `.re0/iteration/active/<version>-<workname>/` into `.re0/iteration/completed/<version>-<workname>/`, unrenamed. `.re0/` is gitignored and untracked, so use `mv` (filesystem move), never `git mv`, which fails on an untracked path. Skip this when the cycle was never planned with `re0-plan` and has no matching iteration folder.

## Rules

- Never invent or assume a CLI command or flag; verify it against official docs or a real run before writing it into a step you will execute.
- Landing the commit and pushing the tag are the whole manual part. Never perform by hand any step the release workflow owns, publishing or titling the release page included, even to rescue a failed run. Re-cutting the author's own defective tag (step 10) is the one exception, and it is pushed again so the workflow still does the rest. A manual run can look successful while omitting the workflow's signed provenance attestation, title convention, or distribution tag; only comparing with the previous release reveals the loss.
- Never push a tag before every manifest's version equals it. A CI check of the same is a backstop, not the first defense.
- Earlier tags are history, not precedent. A new note follows step 6 and passes `notes.mjs` whatever the nearest tag did, a convention read off an earlier note is checked against step 6 before it is applied, and an earlier tag's message is never run through `notes.mjs` to find work nor rewritten to satisfy it.
- The signed tag's message is the note's source, and the GitHub Release body is a copy the workflow writes from it. A note fixed after tagging is fixed by re-cutting the tag (step 10), never by editing the Release body, which the next run overwrites. Where the workflow runs `notes.mjs` on the tag's message, as this repository's does before publishing, a failure there stops the release and the fix is a re-cut tag.
- **negatives-as-corpus**: retirement moves the iteration folder, never deletes it; if the release fails or is rolled back, the folder stays live.
- The human decides at every stop, each its own question: a procedure gap or a split (step 1), an open question that bears on the bump (step 2), the proposal and its local commit (step 8), landing and tagging (step 9), a re-cut tag (step 10), and each comment on a contribution (step 11). An approval never stretches to a later stop. The run ends where the last approval ends, and what remains is reported, never offered.

## Verification

Before finishing, confirm and report:

1. Every manifest's version matches the tag.
2. The commit message reads as a clean handoff without the diff.
3. `notes.mjs` exited 0 on the release notes, and each step 6 rule marked *(judgment)* has a verdict.
4. The first confirmation showed the whole proposal of step 8, `sip`'s run or skip included, no version was named while a question bearing on it stayed open, and the run went no further than the human approved.
5. The landing path matched the branch rules, and where a pull request landed it, `origin/<branch>`'s tree equalled the approved commit's tree before the tag.
6. The workflow the pushed tag triggered completed successfully, confirmed, where the repository has one, and the Release body matched the tag's message or the mismatch was fixed by rerunning the workflow and reported.
7. No workflow-owned step ran by hand, including to rescue a failed run.
8. Each re-cut tag and each comment on a contribution had its own approval, and each landed contribution was approved before closing, with the credit comment.
9. The shipped cycle's iteration folder was moved from `active/` into `.re0/iteration/completed/`, or correctly skipped because none existed.
10. Any skipped step or unresolved gap is reported.
