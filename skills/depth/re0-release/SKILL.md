Ship a release of the repository this runs in, in one deliberate command: gather what the release carries, check it against the repository's release procedure, commit it, then land, tag and publish once confirmed.

## Goal

A release lands complete and trustworthy: the repository's own procedure met, every manifest version bumped by the kind of change, a commit message that hands off without the diff, release notes in house style carried as the signed tag's message, and a published artifact the release workflow produced on its own where the repository has one. `re0-release` walks a pending change down that path. It calls `sip` when installed, applies commit-economy directly, and never calls another user-invoked skill. Each step that commits or writes in public waits for its own approval (Rules): the first confirmation shows the whole proposal and allows a local commit, the second allows landing that commit, the tag and its push, and a re-cut tag or a credit comment each ask again.

It is **user-invoked**: shipping is a deliberate human action, so only the human runs it, once they have decided to ship.

## Workflow

1. **Gather the release and read the procedure.**
   - The release is every change since the last release tag plus the pending diff: find the tag with `git describe --tags --abbrev=0`, then read `git log <tag>..HEAD` and `git diff <tag>`; in a repository with no tag, start from its first commit. The bump (step 2), the notes and their credits (step 6) are drafted from that whole range, and the release commit itself may carry only the bump.
   - The procedure is the repository's own: the Shipping and Releasing sections of its root `AGENTS.md`, else its `CONTRIBUTING.md`, else none. Check the release against every item it states except the bump and the `sip` run, which steps 2 to 4 own; report a gap and stop rather than guess past it. With no written procedure, say so and go on. Every file named below that the repository lacks is skipped.
   - Read the pending diff for anything that is not this release (an unrelated concern, a file another author or agent staged), propose the split or the exclusion, and wait for the answer before anything below is drafted.
2. **Classify the bump** once every open question that bears on what ships is answered (a missing behavior obligation, a contract question, the split); until then, report the question and name no version. Classify by kind, never by size, against the prior behavior: a fix of wrong behavior, or a docs-only change, is patch; a new capability a user reaches for, including a correct but narrower behavior widened, is minor; a removal with no replacement is major. For skills: a new skill is minor, a fix to one is patch, a skill removed with no replacement path is major. State which case applies, not just the bump. The notes follow the case: only a minor or major release carries a `### New` section (step 6).
3. **Taste-test.** Call the Skill tool with "sip"; on a host with no Skill tool, read `sip`'s `SKILL.md` and follow it. Apply its findings, except one that needs an approval (an `ssotize` consolidation plan, say), which joins the step 8 proposal instead. When `sip` is not installed, say so and skip this step. Either way, keep for step 8 whether it ran, what it found and what it changed.
4. **Bump and run the checks.** Set the new version in every manifest that carries it, to the same value: `package.json`, its lockfile, and plugin manifests such as `.claude-plugin/plugin.json`, where present. Then run the repository's own check and test commands (in paperthin, `npm test` and `npm run check`) and keep their result for step 8; fix a failure before the proposal goes out.
5. **Draft the commit message** to commit-economy from the first draft: one bullet per real, durable change, supporting edits folded in; nothing the diff or version already proves; no co-author tag except a closing `Co-authored-by` trailer that credits a human contributor on a squashed or carried contribution. Match the local log's shape, or, absent one, a subject plus one `-` bullet per change on a single unwrapped line. Rewrite the message as edits develop instead of appending to it. Where step 9 will land through a pull request, the landed subject is this subject plus ` (#<n>)`; check that it fits the repository's commit-message limit (72 characters in paperthin), counting the next pull request number's digits, before step 8. If an existing commit needs cleanup, tell the human to run `/re0-git`; it is user-invoked, so never call it.
6. **Write the release notes** to `.re0/release/RELEASE_NOTES.local.md`, local scratch that becomes the signed tag's message and is never committed. Where `git check-ignore -q .re0/release/RELEASE_NOTES.local.md` says the path is not ignored, add `.re0/` to `.git/info/exclude`, which changes nothing tracked, and say so in the proposal. This is the house style; `scripts/notes.mjs` decides each rule marked *(checked)*, and you decide each marked *(judgment)*:
   - one `##` heading with no version number (`X.Y.Z`) in it *(checked)*, naming the release's durable idea *(judgment)*;
   - one paragraph on one line after the heading *(checked)*, short and present-tense, saying what is true now *(judgment)*;
   - sections in this order, each at most once: one New section (`### New` or `### New: <label>`), `### Also`, `### The catalog (N skills)` (`(1 skill)` for one), and `### Install` *(checked)*; only the sections the release earns, the catalog only when the roster needs re-mapping *(judgment)*;
   - `### New` holds only new capabilities a user reaches for, so it appears only in a minor or major release; a fix or tightening of an existing skill goes under `### Also` *(judgment)*;
   - `### Also` holds only what New does not already say, so a release with a single change carries that one section and Install: an Also bullet that leads with a New bullet's subject fails *(checked)*, and any other repeat is *(judgment)*;
   - every section but Install holds single-line `-` bullets and nothing else, no lead sentence *(checked)*;
   - each New bullet opens with a bold lead *(checked)* that is the skill's name (`` **`name`** ``) or a short label (`**One command.**`), never a whole sentence *(judgment)*;
   - each catalog bullet names a perspective and its skills, plain (`` - `depth/`: `re0`, `shower` ``) or with the perspective bold and described (`` - **`depth/`** (one artifact): `re0` ``), and together they list the N skills the heading counts, each once *(checked)*, which are the real roster *(judgment)*;
   - `### Install` is the last section and not empty *(checked)*. Where `.agents/install-block.md` holds release-notes blocks, Install is the contents of the one for the note's version, its markdown fence lines left out *(checked)*; otherwise it carries the install commands the repository documents (its README's install section) verbatim *(judgment)*;
   - each externally contributed change is credited inline with its PR number and author handle, `(#123, @handle)`, a run of pull requests as `(#123-#125, @handle)`, and each co-author as one more `, @handle` before the closing parenthesis, and no other `#` number appears outside code, link targets and URLs *(checked)*; every external change in the release carries its credit *(judgment)*;
   - every claim about a skill stays inside what that skill's `SKILL.md` says it does, never wider *(judgment)*;
   - skill names and paths in backticks *(judgment)*, and no em dash *(checked)*;
   - nothing the tag or version already proves *(judgment)*.
7. **Check the notes.** From anywhere in the repository, run `node <this skill's folder>/scripts/notes.mjs .re0/release/RELEASE_NOTES.local.md` (in paperthin, the folder is `skills/depth/re0-release`); its header names how it finds the root and the version.
   - Exit 0: every *(checked)* rule holds. Where the repository has no release-notes block for the note's version, the output says Install was not checked against a block; that is a pass, and the *(judgment)* rule on Install covers it.
   - Exit 1 names each failure by line: fix the notes, except an `install-block` failure (line 0), which is fixed in `.agents/install-block.md` because its `release-notes` block has drifted from the route blocks.
   - Exit 2: the check could not run, and its message names the cause to fix before running it again.
   - Then read the notes against every step 6 rule marked *(judgment)* and write a verdict for each.
8. **First confirmation.** Show the human the whole proposal: the range step 1 gathered and its result; the files the commit carries and any split or exclusion; whether `sip` ran, what it found, what it changed and any finding that waits for approval; the bump with its case and every manifest it sets; step 4's check and test results; the commit message and whether its landed subject fits; the release notes with step 7's exit and each judgment verdict; any `.git/info/exclude` line added; and the tag it would cut, `vX.Y.Z`. On explicit approval, apply any approved `sip` finding and rerun step 4's checks and step 7; when either fails, show the failure instead of committing. Then commit; the commit stays local. When the human approves only this, end the run by reporting what remains (steps 9 to 12) and that the notes wait in `.re0/release/RELEASE_NOTES.local.md`.
9. **Second confirmation, then land and tag.** Ask the human to land the commit and publish, naming the path below that applies and the tag. On approval, read the owner, repository and default branch with `gh repo view --json nameWithOwner,defaultBranchRef`, then the branch's rulesets with `gh api repos/<owner>/<repo>/rules/branches/<branch>` and its classic protection with `gh api repos/<owner>/<repo>/branches/<branch>/protection` (a 404 means none). Either one requiring a pull request or reviews makes this the pull-request path.
   - Pull-request path: push the commit as its own branch (`git push origin HEAD:refs/heads/release/vX.Y.Z`), open a pull request titled with its subject (`gh pr create --base <branch> --head release/vX.Y.Z --title "<subject>" --body-file <body>`), wait with `gh pr checks <n> --watch`, then merge with the approved message: `gh pr merge <n> --squash --subject "<subject> (#<n>)" --body-file <body>`. Fetch, and compare the landed commit with the approved one: its tree (`git rev-parse origin/<branch>^{tree}` against `<commit>^{tree}`) and its message (`git log -1 --format=%B origin/<branch>` against the approved subject plus ` (#<n>)` and body). A difference stops the run. Reset the local branch to the landed commit (`git reset --keep origin/<branch>` on it), which the tag then marks.
   - Direct path: push the branch; the tag marks the approved commit.
   - Sign the tag with `git tag -s vX.Y.Z <commit> -F .re0/release/RELEASE_NOTES.local.md --cleanup=verbatim`, confirm `git tag -v vX.Y.Z` reports a good signature, push it with `git push origin vX.Y.Z`, and report which path ran.
10. **Watch the workflow.** The release workflow is the one a pushed `v*` tag triggers (a workflow whose `on: push: tags` matches it). With none, the run stops after the tag push: report that nothing was published, and name publishing as the human's step by the repository's documented route, where it has one.
   - Follow the run to completion and report success or the actual failure; never assume it landed. `gh run list --workflow <file> --branch vX.Y.Z` finds the run, `gh run watch <run-id> --exit-status` follows it, and `gh release view vX.Y.Z --json body,isDraft` must show the notes with `isDraft` false.
   - A failure caused outside the tagged commit (a runner, the network, a service) is rerun with `gh run rerun <run-id> --failed` once the cause is gone; a fix that writes to an account or setting outside the repository waits for the human's approval. A failure caused inside the tagged commit is reported and the run stops, since its fix needs a new commit, and so a new version or a re-cut the human decides on.
   - Once the run succeeded, compare the Release body with the tag's message without its signature block and trailing whitespace. A mismatch is fixed by rerunning the workflow (`gh run rerun <run-id>`), never by editing the body, and reported; steps 11 and 12 go on.
   - A tag cut wrong (its message, signature or target) is deleted and re-cut at the same version; the version moves on only when a published artifact is wrong. A re-cut for the signature or the target keeps the message byte-identical: write the old message, signature block removed, to a file and sign the new tag from it with `-F <file> --cleanup=verbatim`. A re-cut for the message carries new notes, which pass step 7. Read the workflow file at the tagged commit first, since that is the file a re-pushed tag runs, then show the human the tag, the cause and the notes it will carry, and re-cut only on their approval.
11. **Credit the contributions.** The repository's own contribution procedure (in paperthin, `re0-merge`) approves and squash-merges each contribution before it lands, so this step never approves, closes or merges. After confirmed success, for each contribution the release carries, show the human a credit comment that points at the release, and post it only on their approval. A carried contribution that is still open is reported and left as it is.
12. **Retire the cycle**, only after the release workflow succeeded. Move `.re0/iteration/active/<version>-<workname>/` into `.re0/iteration/completed/`, unrenamed, matching the folder by its workname when its provisional version differs from the shipped one. `.re0/` is gitignored and untracked, so use `mv` (filesystem move), never `git mv`, which fails on an untracked path. Where the repository keeps a `TODO.local.md`, remove the entry that linked the moved folder and fix the casebook's relative links in the same step. Skip this when the cycle was never planned with `re0-plan` and has no matching iteration folder.

## Rules

- Never invent or assume a CLI command or flag; verify it against official docs or a real run before writing it into a step you will execute.
- Landing the commit and pushing the tag are the whole manual part. Never perform by hand any step the release workflow owns, publishing or titling the release page included, even to rescue a failed run. Re-cutting the author's own defective tag (step 10) is the one exception, and it is pushed again so the workflow still does the rest. A manual run can look successful while omitting the workflow's signed provenance attestation, title convention, or distribution tag; only comparing with the previous release reveals the loss.
- Never push a tag before every manifest's version equals it. A CI check of the same is a backstop, not the first defense.
- Earlier tags are history, not precedent. A new note follows step 6 and passes `notes.mjs` whatever the nearest tag did, a convention read off an earlier note is checked against step 6 before it is applied, and an earlier tag's message is never run through `notes.mjs` to find work nor rewritten to satisfy it.
- The signed tag's message is the note's source, and the GitHub Release body is a copy the workflow writes from it. A note fixed after tagging is fixed by re-cutting the tag (step 10), never by editing the Release body, which the next run overwrites. Where the workflow runs `notes.mjs` on the tag's message, as paperthin's does before publishing, a failure there stops the release and the fix is a re-cut tag.
- **negatives-as-corpus**: retirement moves the iteration folder, never deletes it; if the release fails or is rolled back, the folder stays live.
- Each approval stops at its own step. The human decides at every stop, each its own question: a procedure gap or a split (step 1), an open question that bears on the bump (step 2), the proposal and its local commit (step 8), landing and tagging (step 9), a fix outside the repository or a re-cut tag (step 10), and each credit comment (step 11). An approval covers its own step and none after it. The run ends where the last approval ends, and what remains is reported, never offered.

## Verification

Before finishing, confirm and report:

1. Every manifest's version matches the tag.
2. The commit message reads as a clean handoff without the diff, and its landed subject fits the repository's limit.
3. `notes.mjs` exited 0 on the release notes, drafted from the whole range since the last tag, and each step 6 rule marked *(judgment)* has a verdict.
4. The first confirmation showed the whole proposal of step 8, `sip`'s run or skip included, no version was named while a question bearing on it stayed open, and the run went no further than the human approved.
5. The landing path matched the branch rules and protection, and where a pull request landed it, the landed commit's tree and message equalled the approved ones before the tag.
6. The workflow the pushed tag triggered completed successfully, confirmed, and the Release body matched the tag's message or the mismatch was rerun and reported; or, with no release workflow, the report says nothing was published.
7. No workflow-owned step ran by hand, including to rescue a failed run.
8. Each re-cut tag and each credit comment had its own approval, and nothing was approved, closed or merged at step 11.
9. The shipped cycle's iteration folder was moved into `.re0/iteration/completed/` with its TODO entry and links updated, or correctly skipped because none existed.
10. Any skipped step or unresolved gap is reported.
