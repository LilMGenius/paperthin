Ship a release of the repository this runs in, in one deliberate command: gather what the release carries, check it against the repository's release procedure, commit it, then land, tag and publish once confirmed.

## Goal

A release lands complete and trustworthy: the repository's own procedure met, every manifest bumped by the kind of change, a landing message that hands off without the diff, release notes in house style carried as the signed tag's message, and an artifact the release workflow publishes on its own where the repository has one. `re0-release` calls `sip` when installed, writes messages to the standard step 5 states, and never calls another user-invoked skill. Each step that commits or writes in public waits for its own approval (Rules).

It is **user-invoked**: shipping is a deliberate human action, so only the human runs it, once they have decided to ship.

## Workflow

1. **Gather the release.**
   - Read the owner, repository and default branch (`gh repo view --json nameWithOwner,defaultBranchRef`), then that branch's rulesets (`gh api repos/<owner>/<repo>/rules/branches/<default>`) and classic protection (`gh api repos/<owner>/<repo>/branches/<default>/protection`, where a 404 means none). A rule read there that requires a pull request or reviews sets the pull-request path. Rules that cannot be read (a 403, an origin that is not GitHub or is a `file://` path, no `gh`) set the direct path, where the server's answer to the push decides.
   - The release branch carries the unreleased changes. On the pull-request path it is the head branch of the open pull request found for the current branch (`gh pr view --json number,headRefName,baseRefName`), checked out; otherwise it is the default branch, up to date with its remote.
   - The release is every change on the release branch since the last release tag (`git describe --tags --abbrev=0`, then `git log <tag>..HEAD` and `git diff <tag>`), from the first commit where there is no tag, plus the pending diff. The bump, the notes, the credits and the landing message are drafted from that range; the release commit itself carries only the bump.
   - The procedure is the repository's own: the Shipping and Releasing sections of its root `AGENTS.md`, else its `CONTRIBUTING.md`, else none, which is said and passed. Check each requirement it states on the release's state (a roster, a manifest, a translation) and report a gap. An action it describes is done by the step below that does it, in the repository's wording where the two differ, and step 8 shows the difference. A file named below that the repository lacks is skipped.
   - A file in the pending diff that belongs to another change or author (an unrelated concern, another agent's staged file) is excluded once its recorded owner (its commits, a TODO entry, a coordination note) has been read; step 8 shows the exclusion.
2. **Classify the bump** once every open question bearing on what ships is answered (a contract question, a behavior obligation the release would lose); until then, report it and name no version. A lost obligation blocks the release until it is restored or the human rules on it. Classify by kind, never by size, against the prior behavior: a fix of wrong behavior, or a docs-only change, is patch; a new capability a user reaches for, a correct but narrower behavior widened included, is minor; a removal with no replacement is major. For skills, a new skill is minor, a fix to one is patch, and a skill removed with no replacement path is major. State the case; only a minor or major release carries `### New`.
3. **Taste-test.** Call the Skill tool with "sip", or, on a host with no Skill tool, read `sip`'s `SKILL.md` and follow it; when `sip` is not installed, say so. Apply its findings except one that needs an approval (an `ssotize` plan, say), which joins step 8. Record whether it ran, what it found and what it changed.
4. **Bump and check.** Set the new version in every manifest that carries it: `package.json` through its package manager so the lockfile follows (`npm version X.Y.Z --no-git-tag-version`), and plugin manifests such as `.claude-plugin/plugin.json`, where present. Run the commands the repository's CI runs, else its documented ones (in paperthin, `npm test` and `npm run check`); with neither, step 8 says so. Fix a failure before step 8.
5. **Draft the messages** to the commit-message standard: the local log's shape, or, absent one, a subject plus one `-` bullet per durable change on a single unwrapped line; supporting edits folded in; nothing the diff or version already proves; no co-author tag except a closing `Co-authored-by` trailer crediting a human contributor on a squashed or carried contribution. The release commit's message covers only the bump. On the pull-request path the squash keeps only the landing message, so it covers the whole range: its subject, then one bullet per durable change, the bump last; its subject plus ` (#<n>)`, counting the pull request number's digits, fits the repository's limit (72 characters in paperthin). Rewrite each message as edits develop. An existing commit that needs cleanup goes to the human as `/re0-git`, which is user-invoked and never called.
6. **Write the release notes** to `.re0/release/RELEASE_NOTES.local.md`, local scratch that becomes the signed tag's message and is never committed. Where `git check-ignore -q` finds that path not ignored, add `.re0/` to the file `git rev-parse --git-path info/exclude` names, which changes nothing tracked. The house style; `scripts/notes.mjs` decides each rule marked *(checked)*, and you each one marked *(judgment)*:
   - one `##` heading with no version number (`X.Y.Z`) in it *(checked)*, naming the release's durable idea *(judgment)*;
   - one paragraph on one line after it *(checked)*, short and present-tense, saying what is true now *(judgment)*;
   - sections in this order, each at most once: `### New` (or `### New: <label>`), `### Also`, `### The catalog (N skills)` (`(1 skill)` for one), `### Install` *(checked)*; only those the release earns, the catalog only when the roster needs re-mapping *(judgment)*;
   - `### New` holds only new capabilities a user reaches for; a fix or tightening of an existing skill goes under `### Also` *(judgment)*;
   - `### Also` holds only what New does not say, so a single change is one section plus Install: an Also bullet leading with a New bullet's subject fails *(checked)*, any other repeat is *(judgment)*;
   - every section but Install holds single-line `-` bullets and nothing else *(checked)*;
   - each New bullet opens with a bold lead *(checked)*: the skill's name (`` **`name`** ``) or a short label (`**One command.**`), never a whole sentence *(judgment)*;
   - each catalog bullet names a perspective and its skills, plain (`` - `depth/`: `re0` ``) or bold and described (`` - **`depth/`** (one artifact): `re0` ``), listing the N skills the heading counts, each once *(checked)*, which are the real roster *(judgment)*;
   - `### Install` is the last section and not empty *(checked)*: the contents of the `.agents/install-block.md` release-notes block for the note's version, fence lines left out, where one exists *(checked)*, else the install commands the repository documents, verbatim *(judgment)*; with neither, report the gap;
   - each external change is credited inline as `(#123, @handle)`, a run of pull requests as `(#123-#125, @handle)`, each co-author as one more `, @handle`, and no other `#` number appears outside code, link targets and URLs *(checked)*; every external change in the range carries its credit *(judgment)*;
   - every claim about a skill stays inside what that skill's `SKILL.md` says it does *(judgment)*;
   - skill names and paths in backticks *(judgment)*, no em dash *(checked)*, and nothing the tag or version already proves *(judgment)*.
7. **Check the notes** from anywhere in the repository: `node <this skill's folder>/scripts/notes.mjs .re0/release/RELEASE_NOTES.local.md --version X.Y.Z` (in paperthin the folder is `skills/depth/re0-release`). Exit 0 means every *(checked)* rule holds; "Install not checked against a block" is a pass, and the *(judgment)* rule on Install covers it. Exit 1 names each failure by line, fixed in the notes, or, for an `install-block` failure at line 0, in `.agents/install-block.md`. Exit 2 means the check could not run, and its message names the fix. Then write a verdict for each *(judgment)* rule. Only a reported failure or a verdict's fault changes the text.
8. **First confirmation.** Show the whole proposal in one message: the release branch and range; the procedure's result and any difference from this skill; the files the commit carries and any exclusion; whether `sip` ran, what it found and changed, and any finding awaiting approval; the bump, its case and every manifest it sets; step 4's results; both messages, with the landing subject's length; the full notes, Install included, with step 7's exit and each verdict; any exclude line added; and the landing path, the rule that set it, and every public write it makes: pushing the release branch, opening a pull request or retitling the open one and replacing its body, the squash merge, the tag `vX.Y.Z` and its push. Where `gh` is missing, say that landing or watching then falls to the human, and how. A change to the exclusion, or to anything the notes depend on, means redraft and show again. On approval, apply any approved `sip` finding, rerun steps 4 and 7, and commit when both pass; the commit stays local.
9. **Second confirmation, then land and tag.** In the same run, ask to land and publish, naming the path and every public write step 8 listed. On approval:
   - Direct path: `git push origin <release branch>`. A rejection naming a protection rule (a required pull request, review or status check) switches to the pull-request path, said with its reason; any other rejection stops.
   - Pull-request path: `<body>` is a file holding the landing message after its subject line. Push the release branch (from the default branch, as `HEAD:refs/heads/release/vX.Y.Z`). Retitle the open pull request step 1 found (`gh pr edit <n> --title "<subject>" --body-file <body>`), or open one (`gh pr create --base <default> --head <head> --title "<subject>" --body-file <body>`). Before merging, the branch must contain its base (`git merge-base --is-ancestor origin/<default> HEAD`); when the base moved, update the branch, rerun steps 4 and 7, and show the result for approval again. Wait with `gh pr checks <n> --watch`, merge with `gh pr merge <n> --squash --subject "<subject> (#<n>)" --body-file <body>`, fetch, and compare the landed commit with the release branch: its tree with the branch's, its message with the landing message. A difference stops the run. Then move the release branch to the landed commit (`git reset --keep origin/<default>` on it). Without `gh` or a GitHub origin this path stops here, and the human lands the commit.
   - Sign the tag on the commit that landed, `git tag -s vX.Y.Z <commit> -F .re0/release/RELEASE_NOTES.local.md --cleanup=verbatim`, confirm `git tag -v vX.Y.Z` reports a good signature, `git push origin vX.Y.Z`, and report the path that ran.
10. **Watch the workflow.**
   - Find the tag's run with `gh run list --branch vX.Y.Z`, retrying for about a minute; follow it with `gh run watch <run-id> --exit-status`; `gh release view vX.Y.Z --json body,isDraft` must show the notes with `isDraft` false.
   - With no run, read the workflows at the tagged commit. None with an `on: push: tags` pattern matching the tag means nothing was published, and publishing is the human's step by the repository's documented route. A matching one that started no run, or whose run cannot be seen, is reported as not observed, and the run stops.
   - A failure caused outside the tagged commit (a runner, the network, a service) is rerun with `gh run rerun <run-id> --failed` once the cause is gone. A failure caused inside it is reported and the run stops, since its fix needs a new commit.
   - After success, compare the Release body with the tag message minus its signature block and trailing whitespace. A mismatch is reported and fixed by rerunning the workflow (`gh run rerun <run-id>`), never by editing the body; the publication approval covers that rerun, and steps 11 and 12 go on.
   - A tag cut wrong (its message, signature or target) is deleted and re-cut at the same version; the version moves on only when a published artifact is wrong. A signature or target re-cut signs the old message, signature block removed, from a file with `-F <file> --cleanup=verbatim`, byte for byte; a message re-cut carries new notes, which pass step 7. Before a re-cut, read the workflow file at the tagged commit, since that is the one a re-pushed tag runs, and show the human the tag, the cause and the notes it will carry.
11. **Credit the contributions.** Where the repository's contribution procedure approves and merges each contribution before it lands (in paperthin, `re0-merge`), this step never approves, closes or merges. After success, show a credit comment pointing at the release for each contribution the release carries, and post it on approval; one still open is reported and left as it is.
12. **Retire the cycle** after the workflow succeeded. Move `.re0/iteration/active/<version>-<workname>/` into `.re0/iteration/completed/` with `mv`, unrenamed and matched by workname when its provisional version differs; `.re0/` is untracked, so `git mv` fails. Where the repository keeps a `TODO.local.md`, remove the entry that linked the folder and fix the casebook's relative links in the same step. Skip this when no iteration folder matches.

## Rules

- Never invent or assume a CLI command or flag; verify it against official docs or a real run before writing it into a step you will execute.
- Landing the commit and pushing the tag are the whole manual part. Never perform by hand any step the release workflow owns, publishing or titling the release page included, even to rescue a failed run; a re-cut of the author's own defective tag (step 10) is the one exception, and it is pushed so the workflow does the rest. A manual run can look successful while omitting the provenance attestation, title convention or distribution tag.
- Never push a tag before every manifest's version equals it.
- Earlier tags are history, not precedent: a new note follows step 6 whatever the nearest tag did, and an earlier tag's message is never run through `notes.mjs` to find work nor rewritten for style.
- The signed tag's message is the note's source, and the GitHub Release body is the copy the workflow writes from it; a note fixed after tagging is fixed by a re-cut (step 10). Where the workflow runs `notes.mjs` on the tag's message, as paperthin's does before publishing, a failure there stops the release.
- A rule blocks a push only when it was read or the server rejected the push.
- **negatives-as-corpus**: retirement moves the iteration folder, never deletes it; if the release fails or is rolled back, the folder stays live.
- The stops, each its own question in the same run: a gap (steps 1 and 6), an open question bearing on the bump (step 2), the proposal and its local commit (step 8), landing and tagging, and again after the base moved (step 9), a fix that writes outside the repository and a re-cut tag (step 10), and each credit comment (step 11). An approval covers its own stop only. The run ends when the human declines or defers a stop, or at a stop a step names, and reports what remains without offering it.

## Verification

Before finishing, confirm and report:

1. Every manifest's version matches the tag.
2. The landing message covers the whole range, and its landed subject fits the repository's limit.
3. `notes.mjs` exited 0, and every *(judgment)* rule has a verdict.
4. Every stop in Rules asked its own question, and the run went no further than the human approved.
5. The landing path rested on a rule read or a server rejection, and a pull-request landing matched the release branch's tree and the landing message before the tag.
6. The workflow run completed and the Release body matched the tag message, or the report says what was not published or not observed.
7. No workflow-owned step ran by hand, and nothing was approved, closed or merged at step 11.
8. The iteration folder moved with its TODO entry and links updated, or was correctly skipped.
9. Any skipped step or unresolved gap is reported.
